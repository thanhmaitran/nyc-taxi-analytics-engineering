## 7. Interpretation and limits

**What the run shows (all measured above)**
- Every one of the 197,562,001 source rows is accounted for at every layer: Parquet footers = raw view = rows seen by
  validation = valid (197,539,104) + quarantined (22,897). `fact_trips` equals the valid rows and `quarantine_trips`
  equals the quarantined rows. No file has a duplicated `trip_record_key`.
- Quarantine is small: 22,897 rows = 0.0116% of the source. Reasons: `dropoff_before_pickup` 19,908,
  `pickup_outside_file_period` 2,974, `exact_duplicate_row` 15 (duplicates are detected within a file only).
- Quarantine is concentrated in 2022: 15,078 of 22,897 rows (65.9%). Within 2022 it is highest in 2022-01 to 2022-08
  (0.03% to 0.06% per file). Isolated spikes also appear in 2023-11 (918), 2024-11 (1,128) and 2025-11 (1,459).
  The causes of these spikes were not investigated.
- `cbd_congestion_fee` is NULL for every 2022-2024 row and non-NULL for every 2025-2026 row, as the TLC dictionary
  describes.
- The only dbt warning is `warn_negative_amounts` (56 results, one per file). It is a monitoring test, by design.

**Observations that need a human decision (not errors the pipeline can settle)**
- Negative `fare_amount` rows are kept (policy: warning, not quarantine). They total 4,371,395 (2.21% of rows) and are
  uneven by year: 0.64% (2022), 1.00% (2023), 1.78% (2024), 5.85% (2025), 0.53% (2026). Within 2025 the count falls from
  394,999 in 2025-11 to 48,175 in 2025-12. The cause was not investigated, so no metric excludes or adjusts these rows;
  totals of `fare_amount` and `total_amount` include them.
- Negative distance and unmapped pickup zones are 0 in every file. Lookup IDs 264 ("Unknown") and 265 ("Outside of NYC")
  are valid lookup rows and count as mapped, so "0 unmapped" does not mean every trip has a real NYC zone.
- `request_source` (2026-06 onward) is not in the 2025-03-18 data dictionary and is not loaded into the warehouse.
- The `dim_datetime` range ends at 2026-09-01 00:00 although the last file is 2026-08. That table includes dropoff
  hours, so this is consistent with trips ending just after midnight on 2026-09-01; the run did not query it directly.

**Not measured in this run**
- Benchmark of full refresh vs incremental on the real data (`--skip-benchmark`), and a single-pass vs by-file
  equivalence check on the real data (single-pass runs out of memory on this machine; the equivalence is proven only on
  synthetic data, `docs/results/evidence/`).
- The whole-table `unique(trip_record_key)` test is replaced by a per-file uniqueness check (ADR 0004). Keys embed the
  file name, so per-file uniqueness implies table-wide uniqueness, barring an md5 collision.
- Commit hash is not recorded (the project was not a git repository when run).
- One run, one machine (Windows 11, 8 CPUs, 8.3 GB RAM, DuckDB limit 6 GB): 1,197 s and an 8.60 GB database are single
  measurements, not a performance claim for other hardware.
